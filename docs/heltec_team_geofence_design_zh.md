# Tracker Screen Team 电子围栏设计方案

## 1. 目标与范围

在 Tracker Screen 中提供一个临时电子围栏。Team Leader 可以在 Tracker Screen 上依次添加
顶点并形成一个封闭区域；Team 成员的位置连续超过围栏范围时，设备触发告警。

本方案遵循以下约束：

- 只监控当前 Team 的成员，不检查普通联系人或非 Team 节点。
- Leader 自身不参与越界告警。
- 同一时间只允许存在一个围栏。
- 围栏属于当前 Team 会话，不写入文件系统，设备重启或 Team 解散后清除。
- 只由 Leader 维护围栏并判断成员是否越界，第一版不通过 Mesh 同步围栏。
- 连续超过 3 次才报警，即第 4 次有效位置仍在围栏外时触发。
- 使用固定容量数组，不使用 STL 容器，不因编辑和检测围栏产生长期堆分配。

## 2. 用户界面

### 2.1 Tracker Screen 图标

在 Tracker Screen 左上角放置两个图标：

1. Fence Start：开始创建围栏。
2. Fence Delete：删除已经完成的围栏。

图标状态如下：

| 围栏状态 | Start 图标 | Delete 图标 |
| --- | --- | --- |
| 无围栏 | 可用 | 禁用或隐藏 |
| 正在编辑 | 变为 Cancel | 禁用或隐藏 |
| 已完成 | 禁用或隐藏 | 可用 |

编辑过程中必须允许退出，因此 Start 图标进入编辑状态后临时承担 Cancel 功能，不增加第三个
常驻图标。取消编辑时丢弃尚未闭合的全部顶点。

### 2.2 创建流程

1. Leader 点击 Fence Start。
2. Tracker Screen 进入围栏编辑模式。
3. 用户依次添加顶点，界面绘制顶点及相邻顶点之间的线段。
4. 第一个顶点使用绿色或其他明显样式标记，表示闭合目标。
5. 至少已有 3 个顶点后，当用户在首点附近再次确认时自动闭合。
6. 闭合操作不保存重复的最后一个点，只连接当前末点和首点。
7. 自动退出编辑模式并立即启用围栏检测。
8. 围栏完成后才能删除；删除后才能重新创建。

### 2.3 自动闭合

经纬度不要求完全相等。满足以下条件时自动闭合：

- 当前至少存在 3 个有效顶点；并且
- 新输入点距首点不超过约 15 屏幕像素，或地理距离不超过约 10 米。

屏幕像素条件用于直接操作界面，地理距离条件用于当前位置采点或无触摸设备。最终阈值应根据
实际屏幕尺寸、缩放级别和 GPS 精度测试调整。

第 1 个和第 2 个点不能触发闭合。顶点上限建议为 12；达到上限后停止增加普通顶点，并提示
用户回到首点完成闭合或取消编辑，不自动生成可能错误的闭合区域。

### 2.4 输入方式

触摸设备：

- 点击绘图区添加顶点。
- 点击首点附近自动闭合。
- 屏幕坐标通过 Tracker 视图当前的中心和比例换算为经纬度。

无触摸设备：

- 进入编辑模式后显示十字光标。
- 方向键移动光标。
- 确认键添加顶点。
- 光标位于首点闭合范围内时，确认键完成闭合。
- 返回键取消本次编辑。

两种输入方式最终调用同一套围栏编辑接口，避免维护两套几何逻辑。

## 3. 数据设计

经纬度使用 E7 定点整数，避免长期保存 `double`：

```cpp
struct FencePoint
{
    int32_t latitude_e7;
    int32_t longitude_e7;
};

struct TeamFence
{
    static constexpr uint8_t kMaxPoints = 12;

    FencePoint points[kMaxPoints] = {};
    uint8_t point_count = 0;
    bool completed = false;
};
```

围栏状态建议使用明确枚举：

```cpp
enum class FenceState : uint8_t
{
    Empty,
    Editing,
    Active
};
```

每个 Team 成员保留独立的检测状态：

```cpp
struct FenceMemberState
{
    uint32_t member_id = 0;
    uint8_t outside_count = 0;
    bool alarm_active = false;
};
```

`member_id` 应使用项目中已有的稳定成员标识或公钥摘要，不应只保存联系人数组下标。Team 成员
列表变化后，下标可能指向不同联系人。

成员状态数组按 Team 最大成员数固定分配。Team 变化时清理已经不属于当前 Team 的状态槽位。

## 4. 围栏判断

### 4.1 有效位置条件

只有同时满足以下条件的位置才参与判断：

- 联系人属于当前 Team。
- 联系人不是 Leader 自己。
- 位置数据有效。
- 位置未超过允许的最大年龄。
- GPS 精度满足围栏判断要求。

无定位、定位过期或精度过低时，本次结果记为 Unknown：不增加越界计数，也不清零已有计数，
并且不能产生新的告警。

### 4.2 点在多边形内

围栏启用前必须满足：

- `completed == true`；
- 顶点数量不少于 3；
- 多边形不是明显退化区域。

小范围临时围栏可先以首点或多边形中心作为参考点，将经纬度转换成局部平面坐标，再使用射线法
判断成员点是否位于多边形内部。算法复杂度为 `O(N)`，`N <= 12`，对当前 MCU 的计算压力很小。

局部投影需要考虑参考纬度的经度缩放：

```text
x = longitude_delta * cos(reference_latitude)
y = latitude_delta
```

如未来支持跨越正负 180 度经线的围栏，需要增加经度展开处理；普通本地 Team 活动区域第一版
不要求支持这种情况。

### 4.3 边界抖动

GPS 在边界附近会产生抖动。除了连续次数判断外，建议预留 10～30 米的边界容差。成员位于
容差区域时可保持上一次明确状态，避免在 Inside 和 Outside 之间反复切换。

第一版可以先实现连续次数判断，确认现场 GPS 表现后再启用边界距离容差。边界距离计算不应阻塞
第一版上线。

## 5. 告警状态机

每个成员单独执行以下状态逻辑：

```text
Inside
  └─ 第一次有效越界 → outside_count = 1
       └─ 第二次有效越界 → outside_count = 2
            └─ 第三次有效越界 → outside_count = 3
                 └─ 第四次有效越界 → OutsideAlarm

OutsideAlarm
  └─ 有效位置回到围栏内 → Inside，计数清零并解除告警
```

具体规则：

- 有效位置在围栏外：`outside_count` 饱和递增。
- `outside_count > 3` 且尚未报警：触发一次告警并设置 `alarm_active`。
- 已报警且继续在围栏外：不重复触发。
- 有效位置回到围栏内：计数清零并清除 `alarm_active`。
- Unknown：保持现有计数和报警状态。
- 成员离开 Team：立即删除其围栏检测状态。

告警内容至少包含成员名称。第一版优先支持本机屏幕提示和蜂鸣器；自动发送 Team 消息应作为后续
可配置能力，避免位置抖动或异常数据造成无线消息泛滥。

## 6. 绘制策略

围栏绘制在 Team 成员标记下方：

- 顶点绘制为小圆点。
- 首点使用绿色或特殊圆圈。
- 相邻顶点使用细线连接。
- Active 状态连接末点与首点。
- Editing 状态不连接末点与首点，除非满足自动闭合条件。
- 越界成员使用红色或闪烁标记，其他成员保持原有样式。

不使用全屏 LVGL Canvas。应在现有 Tracker 绘图事件中逐线绘制，避免为 Canvas 申请数 KB 至
数十 KB 的额外缓冲区。

## 7. 生命周期

围栏和成员告警状态在以下情况清空：

- 用户点击 Fence Delete。
- 当前 Team 解散或退出。
- Leader 切换为 Member。
- 创建或加入新的 Team 会话。
- 设备重启。

仅退出 Tracker Screen 时不清空围栏，Leader 应继续在后台接收 Team 位置并进行检测。编辑中的
未完成围栏在离开 Tracker Screen 时应取消，避免后台保留不可见的半成品。

## 8. 模块划分

建议将几何和状态检测从 Tracker Screen 分离：

```text
TeamFenceService
  - 固定容量围栏数据
  - 编辑状态与顶点操作
  - 自动闭合判断
  - 点在多边形内判断
  - Team 成员连续越界状态
  - 告警事件

TrackerScreen
  - Start/Cancel/Delete 输入
  - 光标或触摸点转换
  - 围栏、顶点和成员状态绘制
  - 告警状态展示
```

建议接口：

```cpp
bool beginFenceEdit();
bool addFencePoint(int32_t latitude_e7, int32_t longitude_e7);
void cancelFenceEdit();
void deleteFence();
void updateTeamMemberLocation(uint32_t member_id, const Location &location);
```

`addFencePoint()` 返回值或结果枚举应能区分 Added、Completed、Full 和 Invalid，UI 不自行复制
闭合判断逻辑。

## 9. 资源预算

以 12 个顶点、最多 16 个 Team 成员、不使用 Canvas 为例：

| 项目 | 预计占用 |
| --- | ---: |
| 围栏顶点 | 96 B |
| 围栏及编辑状态 | 16～40 B |
| 成员检测状态 | 128～256 B |
| UI 光标及临时状态 | 50～100 B |
| 预计静态 RAM 增量 | 约 300～500 B |
| 预计 Flash 增量 | 约 6～15 KB |

触摸和按键共用几何服务，仅输入适配不同。计算复杂度约为“成员数 × 顶点数”，在固定上限下可以
视为常量开销。

## 10. 推荐实施阶段

### 阶段一：核心与绘制

- 固定容量单围栏数据。
- 开始、取消、自动闭合和删除。
- 围栏线段和顶点绘制。
- Team 生命周期清理。

### 阶段二：成员检测与告警

- 只处理 Team 成员的新鲜位置。
- 射线法围栏判断。
- 第 4 次连续越界告警。
- 回到围栏内后解除告警。

### 阶段三：输入适配

- 触摸点击选点。
- 无触摸设备十字光标选点。
- 实机调整闭合距离、光标步长和 GPS 精度阈值。

### 阶段四：可选增强

- 边界距离容差。
- 自动发送 Team 告警消息。
- 围栏同步给其他 Team 成员。

阶段四不属于第一版范围。
